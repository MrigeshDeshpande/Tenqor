# 03 — Phase 1 Specification

**Durable Tenant State Machine**

This is the contract for Phase 1. Every semantic here must be implementable as written or explicitly marked `OPEN DECISION`. Phase 1 code may not be written until this document is reviewed and the `OPEN DECISION`s are resolved. No Phase 1 implementation exists yet.

---

## 1. Scope

Phase 1 delivers a **durable, versioned tenant state machine** with:

- tenant model and lifecycle states
- valid transition table with validation
- durable operations with idempotency
- versioning / optimistic concurrency
- crash-safe state transitions
- PostgreSQL persistence
- operation history
- tests for concurrency and failure scenarios

Phase 1 is independently useful: a host application may adopt it to make tenant lifecycle transitions reliable, with no external providers.

### 1.1 Explicitly excluded

- external resource providers / adapters
- resource graphs or dependencies
- reconciliation / desired-state loops
- drift detection
- cloud APIs
- workflow engines
- HTTP server
- production CLI
- distributed deployment

## 2. Domain model

### 2.1 Tenant

```text
Tenant {
  id               TenantId
  lifecycleState   LifecycleState
  version          Version         non-negative integer, monotonically increasing
  metadata         JSON object     domain-neutral payload carried through transitions
  createdAt        timestamp
  updatedAt        timestamp
}
```

Semantics:

- `id` is immutable and externally meaningful; it belongs to the host application. `OPEN DECISION`: UUID format (v4 vs v7) and whether ids are generated by Tenqor or the host.
- `version` increments on **every committed state change**. It is the optimistic-concurrency guard; a transition command carries the version it was computed against.
- `metadata` is opaque to Tenqor. Business data is the host's; Tenqor stores it only as an opaque, versioned payload and never interprets it.
- Phase 1 has **no desired state, no observed state**. Those are Phase 4 concepts.

### 2.2 LifecycleState

Lifecycle states fall into two classes:

- **steady states** — stable, externally observable, no work in flight;
- **in-flight states** — a transition is durably in progress and must be claimed/supervised.

### 2.3 Proposed lifecycle states

| State | Class | Meaning |
| --- | --- | --- |
| `REQUIRES_SETUP` | steady | tenant exists, nothing provisioned yet |
| `PROVISIONING` | in-flight | initial provisioning in progress |
| `INITIALIZED` | steady | tenant is operational |
| `SUSPENDING` | in-flight | suspension in progress |
| `SUSPENDED` | steady | tenant is temporarily disabled |
| `RESUMING` | in-flight | resumption in progress |
| `DELETING` | in-flight | deletion in progress |
| `DELETED` | steady, terminal | tenant is gone, record retained |

**`OPEN DECISION`: the full state set is not final.** The constraints any final set must satisfy:

- every steady state must be reachable from the entry state;
- every in-flight state must be an explicit, durable state (never a transient in-memory flag);
- deletion must be possible from every non-terminal state (interference rules below);
- there must be no valid transition whose meaning is ambiguous to an external reviewer;
- no state may be added or removed after Phase 1 implementation starts without an architecture review.

### 2.4 Proposed transition table

| From | To | Trigger | Notes |
| --- | --- | --- | --- |
| `REQUIRES_SETUP` | `PROVISIONING` | begin provisioning | |
| `PROVISIONING` | `INITIALIZED` | provisioning completed | successful outcome |
| `PROVISIONING` | `REQUIRES_SETUP` | provisioning rolled back | **OPEN DECISION** — do we support rollback-to-unsetup on failure, or does `PROVISIONING` persist until success with a failure record? |
| `INITIALIZED` | `SUSPENDING` | begin suspension | |
| `SUSPENDING` | `SUSPENDED` | suspension completed | successful outcome |
| `SUSPENDING` | `INITIALIZED` | suspension undone | **OPEN DECISION** — on failure, revert to `INITIALIZED` vs. remain `SUSPENDING` until resolved? |
| `SUSPENDED` | `RESUMING` | begin resumption | |
| `RESUMING` | `INITIALIZED` | resumption completed | successful outcome |
| `RESUMING` | `SUSPENDED` | resumption undone | **OPEN DECISION** — same shape as suspension failure handling |
| `INITIALIZED` | `DELETING` | begin deletion | |
| `SUSPENDING` | `DELETING` | begin deletion | **OPEN DECISION** — is a mid-suspension delete legal? This is an interference policy. |
| `SUSPENDED` | `DELETING` | begin deletion | |
| `RESUMING` | `DELETING` | begin deletion | **OPEN DECISION** — is a mid-resumption delete legal? |
| `REQUIRES_SETUP` | `DELETING` | begin deletion | |
| `PROVISIONING` | `DELETING` | begin deletion | **OPEN DECISION** — is a mid-provisioning delete legal? |
| `DELETING` | `DELETED` | deletion completed | terminal |

**`OPEN DECISION`: all interference (delete-from-in-flight) rules.** Constraints: deletion must not be permanently blocked by any state, and a delete must have a defined meaning relative to an in-flight transition (cancel the transition? let it finish? force-abort?).

**`OPEN DECISION`: failure outcome semantics for every in-flight state.** The table must eventually specify, for each transition, what a classified failure means for the resulting state. Until resolved, the spec only requires that failure outcomes are durable and classified ([§9]), never silent.

### 2.5 Transition semantics

- A transition is **atomic and durable**: it commits as a single database transaction ([§8]).
- A transition is **guarded**: it only applies when (a) the current state is in the allowed-from set for that transition and (b) the observed version matches the recorded version.
- A transition is **validated** at the application layer *and* re-validated inside the store transaction. Application-level validation is a convenience; the store-level check is the source of truth.
- The transition table is **closed**: any command that would move a tenant along an edge not in the table is rejected deterministically.
- **Terminal states are terminal** (`DELETED`). No transition leaves `DELETED`. There is no undelete in Phase 1.

## 3. Operation model

### 3.1 Operation

```text
Operation {
  id            OperationId     idempotency key, supplied or generated by Tenqor
  tenantId      TenantId
  type          OperationType   PROVISION | SUSPEND | RESUME | DELETE
  status        OperationStatus
  attempt       non-negative integer
  createdAt     timestamp
  startedAt     timestamp?
  finishedAt    timestamp?
  heartbeatAt   timestamp?      see §8/§9                    (OPEN DECISION mechanism)
  failure       Failure?                                     (OPEN DECISION shape)
}
```

`OperationType` is the **user-level intent**. It may require several internal steps in later phases; in Phase 1 one operation maps to one transition.

### 3.2 OperationStatus

| Status | Meaning |
| --- | --- |
| `PROPOSED` | command accepted, not yet claimed |
| `RUNNING` | claimed, transition in progress |
| `SUCCEEDED` | transition committed, result recorded |
| `FAILED` | transition refused/completed with failure, classified permanent or transient |

**`OPEN DECISION`:** the status taxonomy is provisional. The constraints: statuses must (a) allow replay of a `SUCCEEDED` operation, (b) allow retry of a transient failure, (c) distinguish permanent failure from transient failure, (d) expose in-progress work for takeover.

### 3.3 Operation history

Every attempt, result, and failure is appended to an append-only history for the tenant/operation pair. There is no mutation of history; corrections add new entries. History exists so an operator can answer "what happened, exactly?" without guessing. **`OPEN DECISION`:** whether history is one row per attempt, or one row per transition event; retention policy.

## 4. Command intake

Phase 1 host-facing commands (no HTTP; a programmatic API):

- `createTenant(...)`
- `transition(tenantId, expectedVersion, operationType, operationId, context)`

`createTenant` initializes a tenant at `REQUIRES_SETUP`, version 0, and must itself be idempotent over `tenantId` (an identified duplicate returns the existing tenant; `OPEN DECISION` on duplicate policy — error vs. return-existing).

`transition` is the only mutating use case. All Phase 1 concurrency, idempotency, and crash semantics are defined over `transition`.

## 5. Idempotency semantics

### 5.1 Claims

- Every `transition` call carries an `OperationId` (idempotency key).
- For a given `tenantId`, `OperationId` is unique.
- On receiving a `transition`, the engine looks up the operation:

| Existing operation status | Behavior |
| --- | --- |
| none | proceed to claim and execute |
| `SUCCEEDED` | **replay**: return the recorded success, with the recorded outcome/version; no state change, no effect re-run |
| `RUNNING` | the operation is in flight: do not start a second execution. **`OPEN DECISION`:** block-and-join vs. return "in progress" vs. return a concurrency error. Constraint: must not corrupt or duplicate the running transition. |
| `FAILED` (permanent) | return the recorded failure; no re-run without a new operation id |
| `FAILED` (transient) | **`OPEN DECISION`:** automatic new attempt vs. require explicit retry. Constraint: retry must go through the same claim path (new object state, same operation id). |

### 5.2 Replay guarantee

A `SUCCEEDED` operation replays deterministically to the last caller that consumed it, not by re-executing the transition. This is what makes "timeout but the operation actually succeeded" safe (failure probe #7 in §11).

### 5.3 Why an operation id, not a content or state hash

Hashing the command body cannot disambiguate two *different* commands that mutate toward the same state, and cannot distinguish "one command delivered twice" from "two commands that happen to be identical." The idempotency key is the caller's faithfulness contract. The engine trusts the key and records it.

## 6. Concurrency semantics

Two mechanisms, both enforced at the database (source of truth):

1. **Per-tenant in-flight exclusivity.** At most one operation per tenant may be `PROPOSED`/`RUNNING`. Enforced by a partial unique index over `operations(tenant_id)` where `status IN ('PROPOSED', 'RUNNING')`. A second `transition` for the same tenant while one is in flight is rejected at the store.

2. **Optimistic version CAS.** The tenant row update is:

   ```sql
   UPDATE tenants
      SET lifecycle_state = $next, version = version + 1, updated_at = now()
    WHERE id = $id AND version = $observed
   ```

   Zero rows updated ⇒ stale observation ⇒ the transition must not silently retry; it fails with a version-conflict classification.

Both mechanisms exist because they defend against different races: the first against two *commands* both trying to mutate, the second against a *read-then-write* reaching the database out of order. Keeping both is intentional.

- Interleaving is safe only where the state machine says so (the usable steady states **allow** multiple callers to *observe* and *attempt*, but only one can *commit*).
- Different tenants never contend at the operation level; unrelated tenants proceed in parallel.

## 7. Versioning / generation semantics

- `version` is the per-tenant generation counter. It is the only CAS guard; there is no advisory lock, no separate generation column.
- A version is associated with the **committed state**, not with the attempt that produced it. A caller that observed version N and sends a command expected against N will succeed only if the store is still at N when the command arrives.
- After a successful transition, the store returns the new version. The caller is expected to use it for subsequent commands. Getting it wrong ⇒ version conflict, not silent overwrite.
- `DELETED` records retain their final version. Recreating a tenant with a previous id is `OPEN DECISION` (Phase 1 default: a deleted id may not be reused; recreation is a new id) — constraint: reuse must never conflate historical operation records.

## 8. Transaction boundaries

Phase 1: **state transition + operation persistence = one atomic DB transaction.**

```text
BEGIN
  -- claim: if no in-flight op exists, insert operation row as RUNNING (attempt N)
  --         (enforces per-tenant exclusivity via partial unique index)
  -- validate: tenant exists; current lifecycle_state ∈ allowed-from for type;
  --           observed version == stored version
  -- compute next state from transition table
  -- update tenant: lifecycle_state, version + 1, updated_at
  -- record outcome: operation → SUCCEEDED (+ outcome, finished_at)
  -- append operation history entry
COMMIT    -- atomic: all-or-nothing
```

Failure rules for the transaction:

- any constraint violation, validation failure, or CAS mismatch ⇒ **rollback**, no partial writes, tenant unchanged, operation row absent (claim rolled back too). A failed claim must not leave a phantom in-flight operations.
- a rollback of the claim means the partial unique index never saw a committed `RUNNING` row; a concurrent worker may proceed.
- the store must not call external code inside this transaction ([02 §6]).

**`OPEN DECISION`:** whether in Phase 1 a transition may invoke an in-process "transition work" callback inside the transaction, and its contract. Constraint: the callback performs no I/O outside the transaction, and the Phase 1 code must not depend on it (it is a testing seam for later phases).

## 9. Failure semantics

### 9.1 Classification

Every non-success is classified:

| Class | Meaning | Handling |
| --- | --- | --- |
| **deterministic (permanent)** | the transition is invalid (disallowed edge, terminal state, duplicate-detectable violation) | recorded `FAILED`, no retry, surfaced to caller |
| **transient** | infrastructure/timing: DB connection lost, lock timeout, `40001` serialization failure, network | recorded; retry governed by retry policy (`OPEN DECISION`) |
| **ambiguous outcome** | a commit may or may not have happened from the caller's perspective | resolved through idempotent replay / takeover; never double-applied by naive retry |

Deterministic failures must be **deterministic**: the same input, same tenant version, same store state ⇒ same outcome. No hidden retries ([04]).

### 9.2 Ambiguous outcome resolution

The ambiguity window in Phase 1 is small (no external effects) but the machinery is real:

- A caller that times out re-issues the same `transition` with the same `OperationId`. The engine replays `SUCCEEDED` or reports the durable failure. It never performs a double transition.
- An operator inspecting the store sees: tenant state + operation record + history. If it says `SUCCEEDED`, the transition happened. There is no "maybe".

### 9.3 Retry policy

**`OPEN DECISION`; not implemented until resolved.** Constraint set for any chosen policy:

- must terminate (bounded attempts or explicit operator handoff)
- must not retry deterministic failures
- must not retry across a tenant version change blindly
- must be observable (each attempt in history)
- must be crash-safe (a restart resumes or abandons per the policy, never silently restarts from the top and never double-commits)

### 9.4 Crash safety and stale workers

- **Crash before COMMIT**: nothing is recorded; the store returns to the pre-transition snapshot. Recovery requires nothing.
- **Crash after COMMIT**: the transition is durable. A repeated command replays success (§5.2).
- **Crash between claim and COMMIT** (only possible in the multi-statement Phase 1 path): the claim is rolled back; per-tenant exclusivity is restored. `OPEN DECISION`: whether the Postgres transaction alone suffices for Phase 1, or whether leases/heartbeats are needed at all given no-external-effects constraint. The constraints for later phases: leases must exist before any out-of-transaction side effects are introduced (Phase 3 gate).

### 9.5 Takeover / stale claims

**`OPEN DECISION`; mechanism not yet designed.** Required only if leases exist (§9.4). Constraints: takeover must (a) be safe against the original worker waking up (idempotency + version guard), (b) decide a defined policy for a `RUNNING`-but-stale operation, (c) be observable in history. Until Phase 3, a stale claim must be recoverable by deterministic operator action at minimum.

## 10. Persistence requirements (PostgreSQL)

### 10.1 Tables / constraints (Phase 1 minimum)

```text
tenants
  id              PK
  lifecycle_state state-enum, NOT NULL            CHECK against allowed enum
  version         integer, NOT NULL, CHECK >= 0
  metadata        jsonb, NOT NULL default '{}'
  created_at      timestamptz, NOT NULL
  updated_at      timestamptz, NOT NULL

operations
  id              PK
  tenant_id       FK → tenants(id), NOT NULL
  type            operation-type-enum, NOT NULL   CHECK against allowed enum
  status          operation-status-enum, NOT NULL CHECK against allowed enum
  attempt         integer, NOT NULL, CHECK >= 0
  created_at      timestamptz, NOT NULL
  started_at      timestamptz
  finished_at     timestamptz
  failure         jsonb                            classified failure payload        (shape OPEN DECISION)
  outcome         jsonb                            recorded success payload          (shape OPEN DECISION)

operation_history
  id              PK
  operation_id    FK → operations(id), NOT NULL
  event_type      enum, NOT NULL    (CLAIMED | SUCCEEDED | FAILED | ...)            (set OPEN DECISION)
  attempted_at    timestamptz, NOT NULL
  payload         jsonb

partial unique index
  operations(tenant_id) WHERE status IN ('PROPOSED','RUNNING')
```

### 10.2 Migration and test requirements

- schema managed by Drizzle migrations
- all tests for concurrency/failure gate run against **real PostgreSQL** via Testcontainers, not mocks or an in-memory stand-in
- migrations must be rerunnable and idempotent
- default read committed; the single-transaction transition relies on: partial unique index + CAS update. **`OPEN DECISION`:** whether `SERIALIZABLE` or explicit `SELECT ... FOR UPDATE` is needed, or whether the current two guards suffice. Constraint: no lost update, no lost transition, no concurrent double-commit.

## 11. Acceptance criteria

Phase 1 is accepted when the following are demonstrated by tests against real PostgreSQL plus the concurrency/failure probes in §12.

1. A tenant can be created and driven through every legal transition; every illegal transition is rejected without state change.
2. A `SUCCEEDED` operation, replayed with the same `OperationId`, returns the same result without re-running or changing state.
3. Two concurrent `transition`s for the same tenant: exactly one commits; the other is rejected (not silently absorbed).
4. A transaction rollback leaves no partial writes: tenant state and operation/history tables are consistent.
5. A crash (simulated) before commit leaves the tenant in its previous committed state.
6. A crash after commit leaves the transition durable; replay returns the recorded success.
7. Version CAS: a command computed against an outdated version fails deterministically.
8. Unrelated tenants never block each other (concurrency with multiple tenants progress in parallel).
9. Operation history is append-only and complete for the lifecycle exercised.
10. Every failure recorded is classified (deterministic / transient / ambiguous) or explicitly `OPEN DECISION`.
11. The store abstraction is implemented without `core` importing `pg` or Drizzle ([02]).
12. All tests are reproducible with the documented commands against Postgres 18 (Testcontainers).

## 12. Test scenarios (the failure probes)

Each of the following has an explicit test. Where the semantics above leave a behavior `OPEN DECISION`, the test documents the constraint and is written once the decision is made.

1. **Command arrives twice.** Same `OperationId`, second delivery after first committed → replay, no double transition.
2. **Worker crashes before committing.** No observable state change; no phantom operation.
3. **Worker crashes after committing.** Transition durable; replayed command returns recorded success.
4. **Transaction fails** (forced constraint violation / connection drop). No partial writes; consistent snapshot.
5. **Two workers operate on same tenant.** One claim wins; second rejected at store level.
6. **A stale worker resumes later** (its claim was considered stale and taken over). No double-commit; state remains consistent.
7. **Request times out but the operation actually succeeded.** Retry with same `OperationId` → replay of success, not failure, not double-run.
8. **Process restarts.** Durable state recovered; no lost transitions; in-flight claims handled per policy.
9. **Database connection disappears mid-operation.** Transient failure classification; retry governed by policy; no corruption.
10. **Retry happens after state has already changed** (version mismatch). Deterministic version-conflict failure, no silent overwrite.
11. **Invalid transition attempt** (e.g., suspend from `SUSPENDED`). Deterministic rejection, state unchanged, history records the refusal.
12. **Version conflict on concurrent CAS.** Exactly one writer wins.
13. **Terminal-state tampering.** Any command on `DELETED` is rejected, including creative operation ids.
14. **Idempotency-key collision across tenants.** Same `OperationId` different tenant → independent operations (keys are per-tenant).
15. **History integrity.** Attempts are recorded append-only; no entries mutated after commit.
